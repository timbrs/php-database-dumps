# Рабочий цикл настройки выгрузки

Цель — обезличенный дамп, в котором есть **все виды данных**, какие есть в БД: сто красных клиентов,
сто зелёных, сто заблокированных, все статусы задач, все типы атрибутов. Программа решает, сколько
каких; агент по коду и человек — какие виды бывают там, где база молчит.

## Шаги

1. **`app:dbdump:prepare-analysis`** — слепок схемы `{data_dir}/analysis/schema_inventory.json`
   (+ пер-схемные файлы): таблицы, колонки, размеры по статистике планировщика, профили колонок из
   `pg_stats`, коды после PII-шлюза, внешние ключи. К данным не прикасается: `COUNT(*)` — только на
   небольших таблицах, выборка — `TABLESAMPLE`, всё под `statement_timeout` и бюджетом запросов.
   Здесь же появляются `dossier.<schema>.json` (досье по каждой таблице и колонке: связи, enum'ы
   с доказательствами, миграции, вьюхи, пометки `ambiguous`) и `decisions.<schema>.json` —
   предложения правил R1…R11.
2. **`app:dbdump:prepare-config`** — черновик `dump-settings/*.yaml`: режим таблицы, порядок,
   `cascade_from` по FK, `faker` по именам колонок, `sample.criteria` по категориальным колонкам.
3. **`app:dbdump:apply`** (он же `apply-analysis`) — записывает решения в конфиг. Механическое
   (`auto`) применяется само: маскирование колонки с ПД-именем, связь по внешнему ключу БД,
   удаление таблицы, которой в базе нет, замена заведомо неподходящего паттерна. Остальному нужна
   отметка `accepted` — её ставит агент по коду или человек. Существующее значение в YAML побеждает
   без `override`; решение, исходившее из другого состояния конфига, помечается `stale` и не
   применяется. Итог с провенансом — в `analysis/apply-report.json`.
4. **`app:dbdump:check`** — все проверки одной командой, стадии по наличию БД и дампов:
   `static` (конфиг против слепка, без БД), `live` (критерии и корзины на живой БД под таймаутом),
   `plan` (что и как будет выгружено), `dump` (что реально легло в файлы), `import` (контрольная
   заливка в scratch-БД по `--import-connection`). Один JSON, одно пространство кодов, `--fail-on`.
   `--fix` применяет механически однозначные правки. Коды — в `FINDINGS.md`.
5. Правки по находкам: механические — инструмент, состав выборки (`sample`, `stratify`,
   `stratify_via`, `cascade_from`) — агент по коду и человек, через решения и `apply`.
   Повторить `check`, пока нет ошибок.
6. **`app:dbdump:export all`** — выгрузка. Каскад входит в базовое условие каждой корзины; ход
   выборки — в `analysis/sample-report.json` (пустые корзины, усечения, источник значений).
7. **`app:dbdump:check --stage=dump`** (или `verify-dump`) — сироты по связям, покрытие значений,
   персональные данные в колонках без `faker`, число строк и **корзины по `sample-report.json`**:
   пустая, упавшая или урезанная потолком. Пустую корзину не видит больше никто — критерий
   отработал, ошибки не было, просто ничего не нашлось, и вида данных в дампе нет. Значения
   данных в отчёт не попадают.
8. **`app:dbdump:import`** в scratch-БД — отчёт I-1…I-4: пропущенные таблицы, число строк,
   sequence, внешние ключи. Ошибки в отчёте дают ненулевой код возврата.
9. **`app:dbdump:checkpoint --save`** — зафиксировать «здесь дамп признан годным». Дальше цикл
   идёт по изменившемуся: `checkpoint` без `--save` показывает грязный набор, а
   `check --since-checkpoint` сразу сужает проверку до него.

## Инкремент

Первый прогон — полный. Дальше перепроверять всё незачем: отметка (`checkpoint.json`) хранит
самую новую миграцию, время слепка, коммит и хеши по каждой таблице — настройки, состав колонок,
набор кодов, внешние ключи. Четыре сенсора отвечают на «что могло измениться»:

| сенсор | что ловит | почему без него нельзя |
|---|---|---|
| миграции | версии новее отметки | колонка появляется миграцией — основной путь изменений |
| конфиг | хеш настроек таблицы | правку YAML руками не увидит никто другой |
| слепок | колонки, коды, внешние ключи | новое значение `status_id` приходит без миграции |
| git | файлы миграций после коммита отметки | ловит откаты и правки уже применённых миграций |

Грязный набор — `analysis/dirty.json` с причиной по каждой таблице. Он же подаётся дальше как
есть: `check --tables-from=…/dirty.json`. На схлопнутой истории (`clone --depth=1`) git-сенсор
честно докладывает, что отключён, — остальные три работают. Отметки нет — грязное всё, и это
означает «нужен полный цикл», а не «изменений не найдено».

## Что где лежит

- `{data_dir}/dump_config.yaml` + `dump-settings/<schema>.yaml` — конфиг выгрузки;
- `{data_dir}/analysis/checkpoint.json` — отметка проверенного состояния; `dirty.json` — что
  перепроверять;
- `{data_dir}/analysis/schema_inventory*.json` — слепок; `dossier.<schema>.json` — досье;
  `decisions.<schema>.json` — предложения (контракт в `decisions_schema.json`);
  `apply-report.json` — что из них записано и почему; `sample-report.json` — ход выборки;
  `docs/` — эта документация, `DOSSIER.md`, `COMMANDS.md`, `FINDINGS.md`;
- `{data_dir}/dumps/<schema>/<table>.sql` — дампы.

## Границы

Инструмент никогда не отдаёт наружу значения данных, кроме кодов, прошедших PII-шлюз
(короткие строки без признаков персональных данных, ≤ 50 различных). Агенту к БД ходить не нужно:
всё, что можно узнать безопасно, уже в слепке и в отчётах `check`.
