# Досье: что инструмент знает о таблице и колонке

`{data_dir}/analysis/dossier.<schema>.json` — то, с чем идут к агенту по коду. Слепок БД, код
хоста, конфиг выгрузки, миграции и представления собраны в один файл на схему, а всё, чего
инструмент не знает, помечено явно.

**Значений данных здесь нет.** Единственное исключение — «коды»: короткие идентификаторы
(`1`, `-4`, `RED`), не больше пятидесяти различных, из колонки без ПД-имени, прошедшие шлюз.
Они нужны, чтобы сверить перечисление из кода с тем, что реально лежит в базе. Всё остальное —
имена, типы, счётчики и доли.

## По таблице

| поле | что в нём |
|---|---|
| `row_count` | `{value, estimated, source}` — оценка планировщика, а не точный счёт; `value: null` означает «статистики нет, выполните ANALYZE» |
| `config` | `mode`, `limit`, `where`, `order_by`, `sample`, `cascade_from` — как таблица настроена сейчас |
| `traits` | `dict` (словарь), `scd2` (версионность), `active_flag`, `eav` (атрибуты: роль и парная таблица), `in_degree` — сколько связей ведёт к таблице, `columns` |
| `edges` | связи: `dir`, `table`, `column`, `parent_column`, `source`, `in_db_fk`, `evidence` |
| `views` | представления, которые читают эту таблицу |
| `migrations` | `introduced_in`, `last_changed_in`, `description` (по-русски, своими словами — единственное место, где сказано, зачем), `dml_rows`, `ddl` |
| `code` | сущность, репозиторий, число упоминаний |
| `phantom` | `true` — таблица есть в конфиге, но её нет в базе: ни один экспорт её не выгрузит, и молча |

**`source` связи** говорит, откуда она известна: `db_fk` — внешний ключ в базе, `config` —
`cascade_from` в настройках, `code_doctrine` / `code_migration` — код (маппинг Doctrine или
`FOREIGN KEY` из миграции). При расхождении **`db_fk` побеждает**: база — единственный источник,
который не может ошибаться насчёт себя. Сегодня внешних ключей в базе может не быть вовсе — тогда
весь граф держится на коде и конфиге, и это видно по `source` каждого ребра; отдельное поле
`in_db_fk` отвечает ровно на вопрос «подтверждена ли связь ключом в базе».

**`eav.pair`** — имя второй половины пары «значения ↔ словарь атрибутов». Роль (`values` /
`dictionary`) выводится из имени таблицы, а вот имя пары берётся не из конвенции `<x>_attrs` +
`<x>_attrs_dict`, а из слепка: сначала проверяется, есть ли такая таблица, затем словарь ищется по
связи от `attr_id`. Не нашлось — `pair: null`. Имени, за которым нет таблицы, в досье не бывает:
по нему пошли бы искать.

## По колонке

| поле | что в нём |
|---|---|
| `type`, `nullable`, `pk` | из слепка |
| `profile` | `n_distinct`, `null_frac`, `categorical`, `codes` (после шлюза), `codes_source`, `date_range` |
| `enum` | `class`, `backing`, `cases`, `confidence`, `bridge`, `evidence`, `alternatives` |
| `usages` | где колонку читают, пишут, фильтруют, соединяют, сортируют |
| `pii` | `by_name`, `by_values`, `faker` — как определили и чем маскируется |
| `coverage` | `covered_by` — чем вид данных попадает в дамп, `gap_cases` — какие не попадают |
| `ambiguous` | причины, по которым нужен человек или разведка |

**Перечисление к колонке привязывается тремя способами**, и `bridge` говорит каким: атрибут
сущности (`enumType`) — надёжно; код в одном выражении (сеттер, параметр запроса, сырой SQL) —
чаще всего именно так, потому что атрибут проставлен у единиц колонок; соглашение об именах
(`job_type` ↔ `JobTypeEnum`) — слабее всего, поднимается до среднего, только если все значения
перечисления встречаются в базе. Нескольких кандидатов видно в `alternatives`.

## Пометки `ambiguous`

Досье не притворяется всезнающим. Каждая пометка — вопрос к разведке по коду, а не дефект:

| пометка | о чём спрашивать |
|---|---|
| `enum_db_mismatch` | перечисление знает значения, которых в базе нет (или наоборот) — какое из двух отстало |
| `no_code_mentions` | колонка есть, а в коде её не читают: она ещё нужна? |
| `raw_sql_literal_without_enum` | в сыром SQL сравнивают с числом, которому не нашлось перечисления |
| `introduced_by_migration_without_description` | колонка появилась миграцией, у которой нет описания — за ней идут в задачу |
| `enum_candidates` | кандидатов на перечисление несколько, выбор по имени ненадёжен |
| `coverage_gap` | вид данных в колонке есть, а в выборку не попадает |

## Что с этим делают

Досье само ничего не меняет. По нему правила составляют `decisions.<schema>.json` — предложения
с обоснованием и ссылками на доказательства; контракт этого файла — рядом,
`decisions_schema.json`. Механическое инструмент применяет сам, остальное ждёт отметки от агента
или человека. Порядок целиком — в `WORKFLOW.md`.
